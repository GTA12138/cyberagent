# Runtime 与模型预算独立架构审查

日期：2026-10-23。对象：`E:/cyberagent/artex-ymh-main/artex-ymh-main`。这是源码审查与修改后的静态复核，不是生产验收、真实站点验证或精确账单核对。

## 结论

本轮把框架的两个关键边界做得更清楚：宿主行为归属到 Server 实例，任务模型预算归属到 PostgreSQL 中的任务账户。Runtime 快照、工具调用时保留宿主依赖、持久化预留、幂等结算和归档恢复体现了实质性的系统设计能力，已经超出“把功能接到一起”的阶段。

预算的可成立声明应是：对已经接入的具体 provider 调用，在请求前以保守估计预留容量，完成后结算，失败或缺少可信用量时保守记账；数据库负责串行准入。它不是供应商精确计费系统，也不是所有 tokenizer、供应商隐式提示和 SDK 内部 HTTP 重试的数学硬上限。

本次首轮发现的池内重试/裁判预算覆盖缺口已被具体 provider 层的 dispatch 接线修复。当前主要风险是部分用量可信度、失败状态收口和异常预留的管理恢复；下列各项须结合“最终处置”阅读。

## 本轮设计中成立的部分

### Runtime 归属清楚

`agent/runtime.go:10` 定义构建后发布的实例依赖契约；`WithRuntime` 存储值快照。`agent/assembly.go:64`、`:90` 将宿主 Runtime 随工具绑定，并在 Call 使用新的调用上下文时重新叠加，保留取消与任务归因。第二个 Server 无法再通过进程全局回调替换第一个 Server 的工具解析、提示或终止策略。

`agent/runtime_test.go` 以两个并行宿主、缓存工具在新 context 下执行和显式空 Runtime 检查隔离。需要保留的限制是：结构体快照不会深拷贝闭包内部的可变对象，闭包并发安全仍由宿主负责；各 SetRuntime 也应遵守“发布前配置”，而不是当作热更新 API。

### 账本与准入没有第二份内存余额

`budget/budget.go:1`、`:43` 把服务收敛为估计与 Store 契约，余额不驻留于 Service。`db/model_budget.go:28` 使用任务行锁统一并发预留，`:85` 计算“已结算 + 在途预留”；`:107` 在同一个任务锁下结算，`:115` 保证幂等，`:124` 与 `:127` 在同一事务更新账户及调用状态。

账户聚合与调用行属于事务内的物化汇总和明细，不是两个独立决策源。`llm_usage` 仅在首次建账时导入历史；之后活动摘要不参与模型调用准入。Planner 的周期检查是辅助暂停策略，应继续明确其与权威准入的差别。

### 取消、未知用量与归档选择保守策略

`server/model_budget.go` 的结算使用独立 5 秒 context，调用取消不直接取消记账；流式消费者提前停止仍执行 defer。`db/model_budget.go:119` 未知用量至少消耗预留额度；重启不清空 reserved，避免把实际可能已经发生的消费退款。

`db/task_archives.go:589`、`db/task_archives_restore.go:95`、`:290` 已覆盖预算账户、调用明细的快照、热数据清理和按父子顺序恢复。Server 归档先关闭任务执行屏障并等待主执行及旁路问答收口，再取快照；本轮不能仅凭“加了表”就推断跨进程或任意外部写入均受该屏障保护。

## 发现与建议

### R1 / P1：仅输入用量被误当成完整用量

位置：`budget/budget.go:99`、`:100`，`db/model_budget.go:118`。

当前 `known := complete && used.Input > 0` 把整个 Usage 当成单一可信状态。若模型成功返回非空内容，但提供方仅报告输入用量、遗漏输出用量，就会以 known=true 结算 output=0，退回全部输出预留。重复调用可持续绕过输出预算。这与“未知用量保守记账”的合同不一致。

建议至少让输入缺失或输出缺失都走保守结算，并新增 input-only 成功结果的定向用例。长期应按输入/输出分别记录可信度，避免因一个维度缺失而把另一个已经精确报告的维度一起放大。

### R2 / P2：预算归因失败会跳过复测/验证结果收口

位置：`server/conversations.go:520`、`:558`。

`findingBudgetContext` 查询发现失败或发现已不存在时，在安装结果 sealing defer 之前 return。此时已经查到的 pending retest/check 不会进入 failed/stopped，管理页会一直显示等待中的记录。相邻的“读取 retest/check 失败”分支已经实现按 conversation 收口，但新增预算归因分支尚未沿用该保证。

建议在知道结果记录 ID 后立即安装收口 defer，再进行预算归因；或者在归因失败路径显式 seal，并保留能够定位故障的原因。该问题影响任务状态可信度，不意味着应在归因失败时放行未计费模型调用。

### R3 / P2 设计债：预留可保留，但缺少可解释与审计恢复接口

位置：`db/model_budget.go:143`、`db/schema.sql:589`、`budget/budget.go:66`。

重启保留 reserved 是正确的防退款选择。30 秒等待上限也避免了永久占用执行协程。但账户 API 只暴露总额和 pending_calls，调用明细没有运行代次、宿主实例、provider/profile、调用来源或最后错误；管理员无法区分仍在执行的请求、进程退出遗留和结算失败。没有受控恢复入口时，重启后的遗留预留可能永久阻止该任务继续调用。

建议提供按任务查询预留的 ID、创建时间、运行代次、来源和状态，并提供带审计记录的“确认已失联后转 uncertain、按预留保守计费”操作；不要自动释放容量。若未来支持供应商账单校准，使用独立调整分录，不直接重写历史。服务应暴露等待超时、结算失败和遗留预留数量指标。

### R4 / P2 设计债：管理接口不能完整说明余额来源和可信度

位置：`db/model_budget.go:35`、`:143`、`:155`，`server/model_budget.go` 的 `taskBudgetStatus`。

API 的单查询快照是正确的，但 `spent` 混合真实报告与 uncertain 保守收费；uncertain_calls 只有数量，不能解释保守计费占了多少。未首次调用的历史任务返回 tracking=false、spent=0，首次预留又会导入历史用量；若调用方忽略 tracking，用户会看到余额突然变化。历史导入也没有独立 opening balance 分录，所以不能仅用当前明细求和重建账户。

建议在 API 文档明确 tracking=false 表示尚未建账，公开 baseline/imported、observed、uncertain charged 的来源和金额，或增加可审计的期初分录。将任务预算读模型接入管理界面后，再声明管理员已经能够解释预算状态；当前源码没有前端预算 API 消费方。

### R5 / P3：提前停止流时结算失败被静默丢弃

位置：`server/model_budget.go` 的 Stream defer。

消费者停止后无法再 yield 错误，但 `_ = p.settle(...)` 同时丢弃日志与事件。数据库断连时 reserved 会保守留存，资产并未被错误退款；问题是运维只能看到 pending，无法知道它是结算失败。建议记录 reservation ID、task ID 和错误，配合 R3 的修复/核对机制；勿在日志中写模型请求或敏感响应正文。

### R6 / P2：预算包装不应依赖再次读取 profile 名称成功

位置：`server/server.go:637`。

`loadProfileConfig` 成功后又查询一次 ProfileByID，目前 dispatch 与 recorder/旁路元数据绑定一起放在 `p != nil` 分支。若第二次查询瞬时失败或 profile 被并发删除，会成功返回并缓存未接预算的 provider。任务 router 的外层预算仍可保护主要任务调用，但直接使用具体 provider 的裁判路径不再具备这个保证。

建议将 dispatchTaskBudget 无条件放在 profile 元数据分支之后；是否取得显示名称不应决定强制准入策略是否启用。

## 限制与完成口径

1. 输入估计是请求 JSON 字节数加开销，代码已明确它不是供应商 tokenizer。能防明显的并发超额准入，不能证明最终供应商 token 绝不超过输入上限。
2. `agent/provider.go:276`、`:278` 仍允许 SDK 建连/空响应重试。dispatch 位于 SDK provider 外侧，每次 SDK 调用是一笔预留；不等于每次实际 HTTP 尝试都独立记账。供应商可能对未得到完整 Usage 的内部尝试收费，精确账单对齐需要 SDK attempt hook、禁用内部重试或账单对账机制。
3. 输出硬限制依赖 provider 正确传递并且供应商遵守 MaxTokens；错误/缺用量用保守估计处理，不应把它描述为供应商保证。
4. 本轮是模型 token 预算。没有因此完成网络请求数、工具调用数、美元成本或多供应商价格治理。
5. 归档表接线和测试证明预算状态能够保存/恢复，不证明遗留预留已经具有管理恢复能力。

## 框架设计能力与工程成熟度评价

框架分层方向合理：agent 处理执行协议，Server 注入宿主策略，budget 表达领域准入，DB 负责一致性，provider adapter 处理模型边界。这次从全局回调转为实例 Runtime，以及从周期用量检查转为调用前持久化预留，是正确的架构升级。

目前成熟度可评为“功能完整、核心一致性开始成形，正在补齐运行治理”。强项是领域建模、任务上下文、并发执行控制和恢复意识；弱项是包装器组合契约、异常分支收口、按来源解释账本以及人工恢复路径。尚不足以据此宣称达到精确计费或无人值守企业治理水平。

下一步应围绕可验证的不变量收敛：每次已归因的 provider 调用至多一笔预留；每笔预留要么结算要么可被发现并审计处理；失败分支不能留下伪 pending；管理视图能够区分实际报告、保守收费和在途容量。保持这些约束，比继续增加更多局部状态字段更能提升整个框架的可靠性。
