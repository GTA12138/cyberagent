# YMH 独立架构审查

日期：2026-10-23。审查方式：子代理独立只读源码检查；除本报告外未编辑文件。未读取运行配置、密钥、任务数据或日志，未访问外部目标，未自行重跑完整测试。主代理提供的“1574 通过、16 跳过”是初次工程回归信息，不能据此推出自主任务效果或所有路线图已经验收。下文前五项保留最初发现；本轮修复后的实际状态以文末“后续处置与独立复核”为准。

## 结论

**总体设计能力中上，工程上属于机制较完整、合同仍需收拢的单机平台。** 系统已经超出“提示词加工具”的原型：有任务内探索图与共享资产图、原子意图领取、阶段与权限准入、受管资源、独立证据仓、重放验证、上下文压缩和可重复测试入口。这些结构具有明确问题意识。

当前主要短板在跨机制的一致性：同一个“已验证”“预算上限”“共享资源仍被使用”的含义，尚未在所有入口、版本和生命周期上统一。新增功能常同时改 agent、server、db 和提示词接线，扩展成本偏高。现有回归结果说明大量确定性逻辑得到验证，但没有证明自主决策质量、长任务稳定性或完整路线图完成。

## 前五项问题

### 1. P1：合并后的验证没有绑定证据版本，旧结论可以覆盖新材料的语义

证据：`db/finding_merge.go:280`、`db/finding_merge.go:282`、`evidence/store.go:213`、`db/finding_checks.go:62`、`db/finding_checks.go:85`、`db/finding_checks.go:231`、`db/finding_checks.go:236`。

合并会替换摘要、提高严重级别并追加证据，但保留原状态。重验在提交后通过进程内 `OnMerged` 回调发起；若已有活跃 check，创建逻辑返回原 check，它的冻结快照仍是合并前材料。完成 check 时没有比较当前 `evidence_version` 与验证快照的版本。并且回写只作用于 `status='pending'`：原来为 confirmed 的 finding 合并后，即使重验得到 false_positive，也不会被更正。

两个直接后果：pending 的旧快照可以把包含未验证增量的聚合记录整体变成 confirmed；confirmed 的新摘要/新严重级别可以沿用旧确认状态。提交与回调之间的退出或派发失败还会丢失本轮重验意图。

建议将验证对象明确为某个证据修订版；以事务内持久化待验证事件保证可重试，完成时比较被验证版本与当前版本。旧版本结论保留为历史，新增材料的验证状态独立表达，人工处置的保护另设字段，避免用 `pending` 同时承担两个职责。

### 2. P1：任务 token 上限实际是 planner 周期检查，无法约束整项任务

证据：`server/engine.go:938`、`server/engine.go:997`、`server/engine.go:1046`、`server/engine.go:1293`、`server/task_budget.go:43`、`server/task_budget.go:78`、`db/exploration.go:1128`、`agent/capture.go:117`、`agent/capture.go:147`、`agent/compaction.go:521`。

唯一的预算检查位于 planner 一轮开始前。worker 领取新意图、直投恢复以及单个 agent 会话中的后续模型调用均不经过同等检查；没有 open goal 的分支直接绕过 planner。预算总额只汇总已落库的 result，正在运行会话的 usage 尚未计入。并发 worker 可以在下次规划之前持续超用。读取预算或用量失败时也按不限额放行。后台压缩直接调用 provider，未通过同一预算检查。

因此现状可以称“超额后周期暂停”，不能称整任务硬预算。建议把每次模型调用的准入与累计记账放在共享 provider 包装层，区分实际消耗、预留、结算与有限收尾额度，并明确存储异常时的行为。保留 planner 检查作为可见的任务级状态转换。

### 3. P2：finding 元数据仍以尽力同步双写，两个页面和 agent 可能读到不同事实

证据：`db/findings.go:732`、`db/findings.go:738`、`db/findings.go:740`、`db/findings.go:748`、`server/server.go:2430`、`server/server.go:2441`、`server/server.go:2452`。

严重级别、名称和分类修改先更新 findings，然后独立更新探索节点 payload，第二次更新错误被忽略，接口仍返回成功。全局发现视图读取 findings，任务视图和工具会使用节点 payload。这与新建/合并漏洞已经采用同事务写入的合同不一致。第二步异常或两次并发编辑交错即可留下持久分歧。

建议确定 findings 为字段真值源，以读取投影或同事务更新取代尽力同步；对仍需兼容的节点副本增加修订号与修复入口。先把所有生产修改路径统一到同一个领域写入口，再逐步移除重复字段。

### 4. P2：共享会话已有准入授权，但缺少存活租约和删除仲裁

证据：`db/session_access.go:68`、`db/session_access.go:72`、`server/intranet.go:443`、`server/intranet.go:461`、`server/intranet.go:486`、`evals/scenarios.json:41`。

会话共享通过 action grant 实现，代码也明确说明运行中操作不是租约。删除流程按会话查询全部依赖隧道并收尾，随后关闭会话；没有先判断其他活跃任务是否还在使用该资源。管理员可以执行全局删除，但平台缺少默认拒绝、受影响任务说明及明确的强制选项。任务并行及交接越多，这种生命周期耦合越容易中断其他工作。

这是已登记的 T-09 / E06 缺口，不能把现有授权表或逆序清理算作已完成。建议由资源管理层维护任务持有关系、在途占用和过期策略；常规释放只撤销自己的持有，最终回收经过仲裁，强制回收显式展示影响范围。

### 5. P2：宿主接线依赖可变包级全局回调，限制隔离与演进

证据：`agent/assembly.go:34`、`agent/toolcatalog.go:110`、`agent/prompt.go:13`、`agent/wrapup.go:19`、`agent/finding_workflow.go:16`、`server/assembly.go:26`、`server/assembly.go:213`、`server/assembly.go:239`、`server/server.go:193`。

工具解析、可见性、提示词、收尾词和证据开关由 server 写入 agent 包全局函数，其中闭包捕获特定数据库与宿主。第二个实例或测试宿主的接线会改变第一个实例随后创建的 agent 行为；测试也需要保存/恢复这些全局值。当前单进程单宿主可以工作，但难以在同一进程安全进行并行验收、隔离服务或清晰地验证依赖。

这种接线与 server 包承担 HTTP、任务调度、工具组装、资源管理等多职责相互放大。建议引入每个运行时持有的只读依赖对象，显式传入 ToolResolver、PromptResolver、EvidencePolicy 等小接口；迁移时保持现有工具签名和业务行为。该项属于可维护性与隔离缺口，不表示当前单实例必然故障。

## 成熟度与验收边界

- **架构方向：较强。** 双图、角色分离、证据和受管资源之间具有连贯设计；建议继续加强领域写入口、修订号和资源生命周期，不宜仅增加更多工具接线。
- **工程闭环：中等。** 正常路径和并发恢复已有大量防护，本轮修复了漏洞元数据的静默双写与旧版验证回写；仍有回调丢失、软预算和资源生命周期等合同未统一。
- **扩展成本：中等偏高。** 新能力经常横跨 agent / server / db / prompt；按现有边界增加领域服务和实例依赖，有望逐步降低成本，无需整体重写。
- **效果验证：证据尚不足。** `evals/README.md:3` 与 `evals/scenarios.json` 如实登记首批六场景、五项自动化及一项缺口；路由和能力测试主要验证确定性模型，未证明自主任务质量、真实网络效果或完整 26 场景。

本机隔离服务可以完成链路验收并暴露数据、代理和状态合同问题。它不会自动覆盖长时间运行、跨进程崩溃恢复、共享资源竞争或模型决策效果。应继续以当前唯一待办总表管理这些差距，本报告不将路线图声明为全部完成。
